# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

    make                 # build/mellagui (compositor), build/mellagui-term, build/mellagui-calc, build/mellagui-run, build/mellagui-settings, build/mellagui-view, build/mellagui-record, build/mellagui-calendar
    make run             # build + start mellagui on a real VT (EXEC=, TIMEOUT=, HEADLESS=1)
    make asan            # build/mellagui-asan (ASan + UBSan)
    make fuzz-run        # coverage-guided fuzzer of the whole compositor, FUZZ_TIME=60 s (tests/fuzz_server.c, see docs/FUZZING.md)
    build/keymap-test    # layout tables / keymap generator unit test (also run by tests/run.sh)
    tests/run.sh         # all end-to-end tests (needs a built build/mellagui; plus mellagui-term etc. for TestClients)
    MELLAGUI_BIN=build/mellagui-asan tests/run.sh      # same under the sanitizers (exit code 77 / "Sanitizer" in output = failure)
    python3 -I tests/test_mellagui.py TestWindows.test_move_with_titlebar     # a single test
    build/mellagui --backend headless --size 1024x600 --socket t0 --control /tmp/ctl      # manual headless run
    python3 tools/ppm2png.py frame.ppm frame.png                  # to look at a `dump` from the control socket

Only gcc, make, pkg-config and the libdrm headers exist on the dev machine (no libwayland, xkbcommon, libinput,
wlroots, meson ...); nothing may depend on them. No X11 anywhere. Tests need `XDG_RUNTIME_DIR` (the harness sets one).

## Architecture

Single-process, single-threaded epoll loop (`src/loop.c`); a from-scratch Wayland server (no libwayland).
`docs/ARCHITECTURE.md` and the header comments in `src/*.h` are the module contracts; read the header before a `.c`.

Data flow:
* **input**: `input_evdev.c` (or `lm_input_inject` from the headless control socket) → `seat.c`
  (`lm_seat_handle_input`) → `wm.c` first (`lm_wm_key` shortcuts, `lm_wm_pick`/`pointer_button` for frames and panel) →
  only if the wm declines, `wl_keyboard`/`wl_pointer` events to the focused client.
* **output**: client `wl_surface.commit` → `surface.c` copies the shm buffer into the surface's own texture and calls the
  role's `damage` hook → `xdg.c` forwards to `lm_wm_surface_damage` → `render.c` accumulates per-output damage →
  `backend_*.c` `get_framebuffer`/`present` → `output_ready` (page-flip event or 60 Hz timer) → frame callbacks.
* **windows**: `xdg.c` is only a protocol adapter; all policy (placement, focus, maximize, move/resize grabs, workspaces,
  decorations geometry, panel layout with the round logo button that opens the About dialog, the dock, shortcuts) lives in `wm.c`, which also exposes the scene (`lm_wm_scene_for_each`)
  that `render.c` paints bottom-to-top. The wm talks back to clients only through `struct lm_window_ops`.
* **request dispatch** (`server.c`): object table per client, handlers get already-validated/resolved args; protocol
  violations → `wl_display.error` + disconnect. Interface signature tables are hand-written in `protocol.c`
  (opcodes are named in `protocol.h`); `wire.c` is shared with the clients.
* **user configuration**: `~/.config/mellagui/mellagui.conf` (`--config FILE|none`, headless: none; `--print-config` prints the built-in one) is an INI file read by `conf.c` (sections, `key = value`; each section belongs to one module, `conf_line` in main.c only dispatches). So far `[commands]` (terminal, run, settings, view) -> `launchers.c` (which also expands command lines for the dock and `[keys]` `exec`: `@terminal`-style tokens, `a || b` alternatives, `~/`, bare `mellagui-*` found next to the binary); the old `[menu]` section (the MellaGUI app menu is gone, the dock replaced it) is ignored without a warning. The command line wins. Control socket `dock` / `commands` show the result. * **screensaver**: `src/saver.c` (+ `client/mellagui-matrix.c`, the Matrix rain: columns with a bright head and fading trail, mirrored font letters, software drawn through `wlwin`, `--windowed` / `--speed` / `--seed` / `--selftest`). * **screen recorder**: a separate program, `client/mellagui-record.c` (`--start`, `--duration`, `--output`, `--fps`, `--quality`, `--dir`, `--name`, `--codec auto|h264|ffmpeg|mjpeg`, `--list`, `--selftest`; window with Record / Stop, output and fps buttons, keys Space / O / F / Esc; SIGINT / SIGTERM finish the file; env `MELLAGUI_RECORD_DIR`, default `~/Videos`, files 0600, never overwritten; a notification with the path when it is saved). The compositor only hands out pictures through the private `mellagui_capture_v1` global (`src/capture.c`: `list`, `grab(index, wl_buffer)` -> `lm_render_capture` written into the client's wl_shm buffer by `lm_buffer_write` in shm.c -> `ready` / `failed(reason)`; served only to MellaGUI's own programs like the settings, `lm_settings_client_allowed`; refused while the screen is locked). The program keeps a ring of shared buffers, drops pictures identical to the one before, and codes the others with one of three codecs: **ffmpeg** (`client/ffpipe.c`: raw `bgr0` pictures through a pipe to `ffmpeg -use_wallclock_as_timestamps 1 ... libx264 -crf 21 -fps_mode vfr`, fragmented MP4, BT.709 tagged; best compression, optional runtime dependency; env `MELLAGUI_FFMPEG=path|none`), **h264** (own encoder `src/h264enc.c`, see below; one thread; an IDR picture every 5 s), **mjpeg** (`src/jpegenc.c`, up to 4 threads writing in order). `auto` = ffmpeg when `ffpipe_available()`, else own H.264. The Motion JPEG and own H.264 files are written by `src/mp4.c` (index at the end: a killed -9 recording is not playable; H.264 goes in as `avc1` + `avcC` + `stss`); ffmpeg writes a fragmented one that survives a crash. Measured on a real 60 s 2560x1080 recording: MJPEG 77 MB, own H.264 qp 22 2.2 MB (38 dB), x264 0.75 MB. The pointer is in the picture (`lm_render_capture_cursor`: `paint_cursor` on the whole-output picture, also on top of the GL read-back; screenshots stay without it), no sound; the recorder's own window is in the picture only until it is minimized (it is, as soon as recording starts, see the panel tray). The dock has a Record button (icon `record`, a red ring with a dot, `LM_DOCKICON_RECORD`) after Camera; no key by default (`Super+F12 = exec mellagui-record --start` in `[keys]` works, bare `mellagui-*` is found next to the binary). Tests `TestRecord`.
* **H.264 (own encoder and decoder)**: `src/h264.[ch]` (bit writer / reader, the CAVLC code tables of ITU-T H.264 9-5 .. 9-10, integer transforms, quantizer scales, DC intra prediction), `src/h264enc.[ch]`, `src/h264dec.[ch]`. The subset both speak: constrained baseline (profile 66), 4:2:0, one slice per picture, CAVLC, one reference picture, POC type 2, **no deblocking filter** (`disable_deblocking_filter_idc` = 1), macroblock types I_16x16 with DC prediction (luma and chroma), I_PCM (decoder only), P_L0_16x16 with the vector (0, 0) and P_Skip; constant quantizer (recorder: qp = 46 - quality / 4, clamped 10..40, default quality 80 -> 26), BT.709 limited range signalled in the VUI. The encoder keeps its reconstruction in place and compares each macroblock's source pixels with the previous source first (identical = P_Skip at once), else codes the residual against the previous reconstruction (inter) or against DC prediction (intra, chosen when its SAD is clearly smaller); unchanged-after-quantizing = P_Skip. Frame size is rounded down to even, cropping in the SPS covers the rest of the last macroblocks. The reconstruction is **bit for bit what ffmpeg's decoder shows** (checked at sizes 16x16 .. 2560x1080 and qp 10..51, `h264enc.c` and `h264dec.c` agree too: `mellagui-record --selftest`, `TestRecord.test_our_own_h264`). The decoder refuses anything outside the subset with "not supported: ..." (the viewer then tries ffmpeg) and survived 36000 mutated pictures under ASan/UBSan. No motion search (scrolling is coded as changed macroblocks), no rate control; worst case (every macroblock changes) ~67 ms per 2560x1080 picture on one thread.

* **network drives (SMB)**: no mounting at all. `mount.cifs` refuses ordinary users without an `/etc/fstab` `user` line (checked on cifs-utils 7.0), so `client/smb.[ch]` runs `smbclient` (`$MELLAGUI_SMBCLIENT`, package smbclient / samba-client) as the user: `smb_shares` (`-L`, disks only), `smb_ls`, `smb_get` / `smb_put` / `smb_del` / `smb_mkdir` / `smb_rename`, each with a time limit and an optional cancel callback; credentials go in a 0600 `-A` file in `$XDG_RUNTIME_DIR` that is removed at once, never on a command line; names with a quote, `;`, a back slash or a control character are refused in commands (`smb_name_ok`); `smb_explain` turns `NT_STATUS_*` into words; `run()` copes with a caller that ignores SIGCHLD (the file manager does). The file manager shows it as the virtual path `smb://` (the servers: those in `network.conf` (`$XDG_CONFIG_HOME/mellagui/`, `host user|- [legacy]`, 0600, never a password), the default gateway when it is not in the list (`/proc/net/route`, `$MELLAGUI_SMB_GATEWAY` for tests), and the first row *Connect to a server...*), `smb://SERVER` (its shares), `smb://SERVER/SHARE/dir` (`struct netpath`, `net_parse` / `net_join` / `net_parent`; `join_path` and `list_dir` dispatch on `is_net`). Toolbar *Network* / Ctrl+N, Ctrl+K asks for `host`, `user@host` or `host legacy` (SMB1-only routers); a refused guest (`Wrong user name or password` / `Access denied`) starts the P_NETUSER / P_NETPASS questions (stars, never copied) and retries; a server that worked is saved. A file opens as a copy in `$XDG_CACHE_HOME/mellagui/network/...` (at most 64 MB, edits are not sent back); F5 / F6 between a network place and a local folder, F7, F2 and F8 (always for good: no trash) work on the server, in the job thread (`net_copy_node`; the progress bar follows the size of the file being written for a download and smbclient's read position in `/proc/PID/fdinfo` for an upload, `net_poll_progress`, `smb_child_pid`; the upload side was only checked with a stand-in that reads with read(), not against a real smbclient; a move inside one share is a rename, between two servers is refused); no preview, no terminal there; Delete in the list of servers forgets one.   (pty, parser, scrollback, selection/clipboard); `src/font.c` + `src/font_data.h` (generated by `tools/gen_font.py`
  from `/usr/share/consolefonts/Uni2-Terminus16.psf.gz`) and `src/keymap.c` (layout tables → generated XKB keymap + client keysym lookup; `--layouts`, Super+Space, sticky keys live in `input_evdev.c`) are shared with clients.

Gotchas:
* wm coordinates: `lm_window.{x,y,width,height}` is the *window geometry* (client area); the frame is drawn around it
  (see `wm.h`). Workspaces are 0-based in the control socket output.
* Sub-surface position and `set_window_geometry` take effect on the *parent's* commit (protocol-correct; tests rely on it).
* The headless backend's `windows`/`dump`/`sync` commands are the test oracle; add a test in `tests/test_mellagui.py`
  (helpers: `Window`, `Ctl`, `Ppm` in `tests/wlclient.py`) when changing behaviour.
* The XKB keymap text is generated (`lm_keymap_build`) and cannot be compiled here (no libxkbcommon): real xkbcommon clients (VS Code) are the only way to verify it.
* Devices: with a usable logind session (`--logind auto`, default) `src/logind.c` (a from-scratch D-Bus client, `docs/ARCHITECTURE.md`) hands out the DRM and evdev fds and does VT switching (`PauseDevice` → ack, `ResumeDevice`, `Seat.SwitchTo`); otherwise plain `open(2)` + VT_PROCESS, which needs groups `video`+`input`. Backends call `lm_dev_open` / `lm_dev_close` so both paths share the code. Tested only against `tests/fake_logind.py` (`TestLogind`, `build/logind-test`) and by hand up to `TakeControl` on the real logind.
